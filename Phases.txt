B3 — Rules system audit, not construction

The previous roadmap said to create:

categories, rule pages, search, related rules, glossary, staff editor, drafts/publishing

but those systems already exist. The repository already loads active rule categories, published rules, links between rules and published glossary entries. The staff side already creates and edits categories, rules, glossary entries and related-rule links with draft/published workflows.

So B3 should instead be:

verify all Rules UI works correctly;
improve navigation/search if needed;
audit slugs and category organisation;
verify related-rule links;
verify glossary linking;
make the public modal experience coherent;
verify draft material is impossible for players to retrieve directly;
clean up staff editing UX;
add change history later under auditing rather than rebuilding Rules.

C2 — Unified Report system

Reports should use the ticket infrastructure, not become a second disconnected support system.

A report creates a special ticket with type = report.

A report should preserve:

reporter user;
reporter character;
reported character if identifiable;
source type;
source ID;
source URL/context;
reason;
reporter explanation;
creation time;
assignment;
status;
staff notes;
resolution.

Crucially, it should also save a snapshot of the reported content at report time.

Otherwise somebody could report:

“this person wrote an abusive message”

and the author edits/deletes it before staff opens the report.

C3 — Report buttons everywhere required

One reusable Report component/action should support different targets rather than six bespoke reporting systems.

Target types should include at minimum:

forum_topic
forum_post
direct_message
room_message
instant_chat_message

A room message includes both ordinary speech and actions, so every action/message in play can be reported through its room_messages record.

The repository already has all of these separate communication surfaces: forum topics/posts, room messages, direct messages and Instant Chat.

The UI should therefore add:

Forum topic

Report topic

Every forum reply

Report

Every private-message entry

Report

Every room/chat message or action

Report

Every Instant Chat message

Report

Not the whole conversation — the individual offending item.

The report modal should ask for a reason such as:

Harassment
Offensive/inappropriate content
Metagaming / rule breach
Spam
Impersonation
Sexual/inappropriate behaviour
Other

plus optional explanation.

One important distinction: the current forum already contains a concept called flagging, but it is a mechanism for sending/flagging a topic to other eligible characters, not a staff abuse-report system. It should therefore remain separate rather than being repurposed.

C4 — Staff Reports centre

Inside Administration:

Reports

with:

Staff should see:

exact reported snapshot;

For room and messaging reports, I would also provide a small amount of adjacent context — e.g. several messages before and after — only to authorised staff.

C5 — Abuse protection and auditability

Add:

prevent duplicate reports by the same user on the same object while one is open;
report rate limiting;
server-side target verification;
reporters cannot alter report evidence;
reported users cannot see who reported them through ordinary UI;
immutable event/audit history;
staff action log;
report deletion restricted heavily or preferably never physically deleted;
closed tickets retained for audit.

This is also where we eventually connect account moderation/suspension controls.
